# Как работать над LofLume

Ты определяешь, что должно быть удобно и полезно. Агент выбирает реализацию,
пишет код, проверяет результат и поддерживает требования. Читать код и управлять
командами OpenSpec вручную не требуется.

## 1. Открой чат в этом проекте

Стартовая модель — **GPT-6.1 Sol / medium**. Для обсуждения сложной идеи
и архитектуры можно выбрать **Sol / high**. Если новые skills не появились,
открой новый чат проекта; при необходимости перезапусти приложение.

В Codex доступны следующие skills (это сообщения в чат, не команды терминала):

| Skill | Для чего |
|---|---|
| `$openspec-explore` | Обсудить идею и варианты |
| `$openspec-propose` | Подготовить предложение, требования, дизайн и задачи |
| `$openspec-apply-change` | Реализовать подготовленное изменение |
| `$openspec-update-change` | Обновить документы активного изменения |
| `$openspec-sync-specs` | Перенести изменения в актуальные требования |
| `$openspec-archive-change` | Завершить и архивировать изменение |

В desktop-приложении также можно выбрать skill из списка Skills.
Обычный текст тоже подходит: агент подберёт workflow. Названия `/opsx:*`
в документации относятся к другим интеграциям; здесь используем имена выше.

## 2. Расскажи идею

> Хочу сделать [идея]. Пользователь — [кто]. Основная польза — [зачем].
> В первой версии важно [2–3 сценария]. Давай сначала обсудим и подготовим
> OpenSpec-предложение. Технологии выбери сам, учитывай простоту и стоимость.

Если идея ещё сырая:

> $openspec-explore Помоги сузить эту идею до полезной первой версии: …

Explore — обсуждение, без реализации. Агент уточняет значимые вопросы;
технические подробности готовит сам.

## 3. Получи предложение

> $openspec-propose Подготовь первую версию: …

Агент создаст `openspec/changes/<имя>/` с `proposal.md`, `specs/`,
`design.md` и `tasks.md`. Тебе достаточно проверить резюме: правильную ли
задачу решаем, что входит в версию и как проверить результат.

Штатный propose-workflow заканчивается после планирования. Для реализации
нужно следующее сообщение; подтверждать каждую техническую задачу не требуется.

## 4. Дай команду реализовать

> $openspec-apply-change <имя-изменения>

Или:

> План подходит. Реализуй изменение, запусти нужные проверки и покажи,
> как попробовать результат.

Агент пишет код, выполняет проверки и отмечает выполненные задачи.
Валидация OpenSpec проверяет документы; работу приложения проверяем отдельно:
сборкой, тестами и запуском, когда появится код.

## 5. Попробуй и скорректируй

> Попробовал: [что неудобно / что ожидал / что произошло]. Исправь.

Для новых требований внутри текущей работы:

> $openspec-update-change <имя-изменения> Теперь нужно [новое поведение].

После обновления плана попроси продолжить реализацию. Маленькие исправления,
восстанавливающие описанное поведение, делаем напрямую. Новая самостоятельная
функция получает отдельное предложение.

## 6. Закрой готовую функцию

> $openspec-archive-change <имя-изменения>

Агент проверит завершённость и предложит синхронизацию требований, если она нужна.
Для завершённой функции обычно выбирай **Sync now**: актуальные требования попадут
в `openspec/specs/`, история изменения — в архив. Невыполненные задачи нужно
доделать; не архивируем их ради порядка.

## 7. Продолжи после перерыва

В новом чате этого проекта:

> Прочитай AGENTS.md, посмотри активные изменения OpenSpec и продолжи
> <имя-изменения>. Кратко скажи, что сделано и какой следующий шаг.

Всю переписку переносить не нужно: требования, решения и задачи сохранены
в проекте. Изменения вне OpenSpec видны в коде и Git diff, когда подключён Git.

## Модели и экономия лимитов

Это стартовые настройки проекта, а не универсальная таблица стоимости:

| Работа | Модель и effort |
|---|---|
| Обычная разработка понятной функции | GPT-6.1 Sol / medium |
| Архитектура, неоднозначные требования, сложный баг, миграция | GPT-6.1 Sol / high |
| Небольшая понятная правка, механическое изменение | GPT-6 Luna / low или medium |
| Astra, xhigh/max | Только по твоему явному запросу для конкретной задачи |

Агент оценивает сложность и предлагает переключение, когда оно окупится.
**Модель текущего чата переключаешь ты в приложении**: OpenSpec и `AGENTS.md`
не являются автоматическим маршрутизатором. Не нужно переключаться ради каждой
мелочи внутри большой задачи. Твой явный выбор имеет приоритет.

Если используешь Opus в другом клиенте, применим тот же принцип выбора по
сложности. Доступность моделей и настройки effort зависят от клиента.
Здесь установлена интеграция **Codex**, а не Claude Code; параметры Opus
не подменяем догадками и не запускаем его без соответствующего инструмента.

Один агент — стандарт. Субагент допускается по отдельному запросу для ограниченной
задачи. Автоматических команд ревьюеров и QA нет. Сначала используем сборку,
тесты и другие детерминированные проверки, затем решаем, нужен ли дополнительный анализ.

## Терминал: необязательная справка

На этой машине Node не находится в обычном PATH. `./scripts/openspec` использует
установленный Node либо Node из Codex. Вызовы из корня проекта:

```sh
./scripts/openspec --version
./scripts/openspec list --json
./scripts/openspec list --specs --json
./scripts/openspec status --change <имя-изменения> --json
./scripts/openspec validate --all --strict --no-interactive
```

Также доступны `pnpm spec:list`, `pnpm spec:validate`, `pnpm spec --help`.
До появления требований «нет объектов для проверки» — ожидаемый результат,
а не подтверждение работоспособности приложения.

Для новой машины: Node >=22 и pnpm 11.25.0, затем:

```sh
pnpm install --frozen-lockfile
```

Не обновляй инструменты в начале каждой сессии. Для намеренного обновления попроси
агента проверить release notes, обновить закреплённую версию и lockfile, обновить
skills и проверить проект. `openspec update` учитывает глобальные настройки;
чтобы явно сохранить нашу базовую интеграцию, используй:

```sh
./scripts/openspec init --tools codex --profile core --no-animation
```

Генерируемые skills вручную не редактируем. В среде с защищённой папкой `.agents/`
обновление skills может потребовать стандартного разрешения Codex на запись.

## Устройство настройки и источники

- OpenSpec 1.14.3 установлен локально, с lockfile; глобальная установка не нужна.
- Стандартные схема и core-профиль, без собственного процесса поверх OpenSpec.
- `AGENTS.md` содержит постоянные правила; этот гайд читается по необходимости.
- Документы на русском, структурные заголовки OpenSpec сохранены.
- Запускатель отключает телеметрию для своего процесса через документированную
  переменную `OPENSPEC_TELEMETRY=0`. Переменные `XDG_CONFIG_HOME` и `XDG_DATA_HOME`
  направляют настройки и служебные данные CLI в игнорируемую `.cache/` проекта,
  поэтому повторная инициализация не записывает конфигурацию в домашнюю папку.
  Глобальные настройки не менялись; установленный вручную CLI вне запускателя
  не будет использовать эти локальные настройки.
- Стек и команды проверок приложения выберем после обсуждения идеи.
